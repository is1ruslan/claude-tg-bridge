# cc-telegram — мост Claude Code ↔ Telegram (Windows) — дизайн

Дата: 2026-10-26. Статус: черновик на согласование.

## Зачем

Пользователь держит несколько сессий Claude Code в разных проектах (встроенный терминал VS Code, PowerShell, Windows 10, auto mode) и отходит от компьютера. Telegram должен заменять терминал на это время: сообщать, что задача закончилась, присылать вопросы Claude с кнопками, принимать ответы и новые инструкции и доставлять их в нужную живую сессию. Когда пользователь за компьютером — терминал работает как обычно, Telegram не мешает и не дублирует ответы.

Готовых решений под нативный Windows без tmux с несколькими сессиями нет (обзор — в переписке, шаг 1). Пишем своё.

## Цели

1. Бот общается только с одним Telegram user ID (`TELEGRAM_USER_ID`). Любые апдейты (сообщения, нажатия кнопок) от других ID игнорируются молча — без ответа; в лог пишется только факт и чужой ID.
2. Уведомление о завершении задачи:
   ```
   📁 <проект> · <git-ветка>
   Статус: ✅ завершено / ❌ ошибка / ⏸ ждёт решения
   <2–5 строк: что сделано, что осталось, что нужно от пользователя>
   ```
   Шлётся **только если задача длилась ≥ 60 секунд** (от последнего промпта пользователя — из терминала или из Telegram — до Stop). Ошибки (❌) шлются всегда.
3. Вопросы Claude (AskUserQuestion, в т.ч. брейншторм superpowers; подтверждение плана ExitPlanMode; запрос разрешения) → сообщение с вопросом и inline-кнопками `1..N` + «Другое» (для AskUserQuestion) → ответ уходит в ту же сессию, работа продолжается. Вопросы шлются всегда, без порога длительности.
4. Управление: свободный текст в бота → инструкция в нужную сессию. Команды: `/status` (активные сессии и их состояние), `/stop` (прервать текущую работу в сессии).
5. Несколько сессий одновременно: каждое сообщение помечено проектом (и коротким тегом сессии, если в одном проекте их несколько); reply на сообщение или нажатие кнопки маршрутизируется в свою сессию.
6. Информирующие сообщения — без кнопок.
7. Терминал остаётся полностью рабочим: **вопрос показывается и в терминале, и в Telegram одновременно; засчитывается источник, где ответили первым**. Ответили в терминале → сообщение в Telegram помечается «✔ отвечено в терминале», кнопки убираются.

## Не-цели

- macOS/Linux, WSL-сессии Claude Code — не поддерживаем (можно добавить позже).
- Расширение VS Code (панель Claude Code, не терминал) — не поддерживаем.
- Группы Telegram, несколько пользователей, вебхуки (только long polling).
- Передача файлов/фото, голос.
- Отдельные уведомления о завершении субагентов (SubagentStop) — их результат входит в общую сводку сессии (решение автора).

## Анти-цели (провал, даже если «работает»)

- Хук тормозит или роняет Claude Code. Все хуки — асинхронные/fire-and-forget, любые ошибки сети и демона глотаются (логируются), хук всегда exit 0.
- Токен попадает в логи, git или чат.
- Бот реагирует на чужие аккаунты (хотя бы ответом «нет доступа»).
- Ответ в Telegram «молча» приводит к неверному выбору в терминале — любое расхождение должно быть замечено и сообщено.
- Спам: уведомление после каждой короткой реплики.

## Ограничения и окружение

- Windows 10 Pro, Node 22 (nvm4w), Claude Code 2.1.310 (`claude.exe` из `@anthropic-ai/claude-code`), Git Bash есть (хуки по умолчанию исполняются через него), tmux нет.
- Глобальная установка (user scope): хуки в `~/.claude/settings.json` с **слиянием** с существующими настройками (там уже есть superpowers и auto mode — ничего не трогать).
- Сеть: только `api.telegram.org`. Резюме через локальный `claude -p --model haiku` (подписка пользователя), без прямых API-ключей.
- Секреты: `~/.claude/telegram/.env` с `TELEGRAM_BOT_TOKEN=` и `TELEGRAM_USER_ID=` — **создаём с плейсхолдерами, пользователь вписывает сам**; права только для текущего пользователя (icacls, аналог chmod 600). Токен не просить в чате.
- Репозиторий кода: `C:\Projects\cc-telegram` (git). Рантайм-данные: `~/.claude/telegram/` (`.env`, состояние, логи).

## Ключевое техническое решение: ввод в консоль сессии

Доставка ответов и инструкций в живую сессию — через Windows API: вспомогательный процесс делает `FreeConsole` → `AttachConsole(pid claude.exe)` → открывает `CONIN$` → `WriteConsoleInputW` (KEY_EVENT записи). Это аналог `tmux send-keys`. Channels (MCP, research preview, флаг `--channels`) **не используем**: не нужны флаги/обёртка над `claude`, нет конфликта поллеров одного токена, не зависим от preview.

Проверено экспериментом 2026-10-26 (скрипт `scratchpad/spike/inject.ps1`, будет перенесён в репо как референс) на живой сессии в терминале VS Code:
- Нажатия доходят; кириллица, длинное тире, латиница — без искажений.
- В AskUserQuestion с одиночным выбором **цифра `k` сразу выбирает вариант k и отправляет ответ**.
- Пункт «Другое» (ввод своего текста) — строка N+1: навигация стрелками вниз до неё, затем ввод текста. После вариантов есть ещё пункт «Chat about this» (N+2) — его не нажимать никогда.
- **Текст и Enter в одной пачке не отправляются** — Claude Code считает это вставкой. Enter (и прочие управляющие клавиши) слать отдельной записью после паузы (~300–500 мс).
- Множественный выбор (`multiSelect: true`) — мастер: Enter переключает галочку на текущем пункте; затем пункт `Submit` под вариантами (стрелка вниз → Enter); затем экран «Review your answers» с «1. Submit answers» (Enter). Вверху вкладки `← ☐ <header> ✔ Submit →`, подсказка «Enter to select · ↑/↓ to navigate · Esc to cancel».
- Несколько вопросов в одном вызове (до 4) — вкладки; последовательность для каждой, в конце экран Review.

Окна подтверждения плана (ExitPlanMode) и запроса разрешения ещё не исследованы — их раскладку клавиш строитель выясняет таким же экспериментом (ожидаемо цифры работают так же). Последовательности клавиш держать в одном модуле с таблицей «тип окна → последовательность», чтобы чинить после обновлений Claude Code в одном месте.

Вспомогательный процесс: маленький C#-exe, компилируемый при установке встроенным `csc.exe` .NET Framework (без внешних зависимостей); принимает pid и последовательность шагов (клавиши/текст/паузы) из stdin или файла. Отдельный процесс обязателен: `AttachConsole` действует на весь процесс.

Обновления Claude Code: демон пишет версию Claude Code (из SessionStart/`claude --version`) в лог; при несовпадении фактического ответа с выбранным (сверка PostToolUse) — предупреждение ⚠ в Telegram, без автоматического отключения. Пиннинга версии и самотеста при установке нет. *(решение автора)*

Известный риск: если пользователь печатает в том же терминале в момент инъекции, тексты смешаются. Принимаем.

## Архитектура

```
Claude Code сессия (claude.exe) ──hooks (async, node)──► демон (127.0.0.1, HTTP + секрет)
                                                           │  long polling ◄──► api.telegram.org
                                                           └─► inject.exe ──WriteConsoleInput──► консоль claude.exe
```

### Демон (`cc-telegram daemon`)
- Один на все сессии, Node 22, без фреймворков (Telegram Bot API через `fetch`). Единственный потребитель `getUpdates` для токена.
- Локальный HTTP на `127.0.0.1` (порт и случайный секрет пишутся в `~/.claude/telegram/state/daemon.json` при старте; хуки читают оттуда). Запросы без секрета отклоняются.
- Хранит состояние сессий в памяти + снимок на диск (переживать рестарт демона): `session_id → {pid claude.exe, cwd, project, branch, state, lastPromptAt, pending dialogs}` и `telegram message_id → session_id / dialog`.
- Автозапуск: Планировщик заданий Windows, задача «при входе пользователя», скрытое окно, перезапуск при сбое. Переживает перезагрузку.
- Логи в `~/.claude/telegram/logs/` с ротацией; токен маскируется.

### Хуки (в `~/.claude/settings.json`, все `async: true`, короткий таймаут)
Хук — `node <repo>/dist/hook.js <event>`: читает JSON из stdin, добавляет `pid`-цепочку (свой ppid), шлёт в демон POST с таймаутом ~1–2 с, всегда exit 0. Если `CC_TELEGRAM_DISABLE=1` или файл `~/.claude/telegram/disabled` — ничего не делает.

| Событие | Что делает демон |
|---|---|
| SessionStart | регистрирует сессию; по ppid-цепочке хука находит pid `claude.exe`; проект = имя папки cwd, ветка = `git branch --show-current` |
| UserPromptSubmit | state=working, `lastPromptAt=now`; закрывает висящие диалоги сессии как устаревшие |
| PreToolUse (AskUserQuestion, ExitPlanMode) | создаёт диалог, шлёт сообщение с кнопками |
| PermissionRequest | создаёт диалог разрешения, шлёт кнопки |
| PostToolUse (AskUserQuestion, ExitPlanMode, и любые для закрытия диалогов разрешений) | диалог закрыт: если ответ пришёл не из Telegram → «✔ отвечено в терминале», кнопки убрать; если из Telegram → сверить фактический ответ с выбранным, при расхождении — ⚠ сообщение |
| Stop | state=idle; если `now - lastPromptAt ≥ 60 с` → уведомление о завершении |
| StopFailure (если событие есть в текущей версии; иначе — ближайший аналог) | ❌ уведомление, всегда |
| SessionEnd | удалить сессию, закрыть её диалоги |

Демон также периодически проверяет, жив ли pid; мёртвые сессии удаляет.

### Сообщения
- Заголовок каждого: `📁 <проект> · <ветка>` (+ ` #<4 символа session_id>` если в проекте несколько живых сессий).
- **Завершение:** текст из `last_assistant_message`. Если коротко (≤ ~5 строк и ≤ ~500 символов) — как есть; иначе сжать `claude -p --model haiku` (с `CC_TELEGRAM_DISABLE=1`, чтобы не зациклить хуки) до 2–5 строк по сути. Тот же вызов определяет статус ✅/⏸ (⏸ — если Claude ждёт решения/задал вопрос в тексте). При сбое haiku — обрезанный исходный текст, статус ✅. Haiku выбирает из трёх: ✅ / ⏸ / ❌ (❌ — Claude сам сообщает о неудаче: тесты красные, не смог доделать). Такой ❌ подчиняется порогу 60 с; без порога шлётся только ❌ из StopFailure. *(решение автора)*
- **Дубли у компьютера — намеренно:** пользователь выбрал «вопрос и в терминале, и в Telegram, засчитывается первый ответ», а уведомления о завершении — по порогу 60 с независимо от присутствия. Детекции присутствия нет.
- **AskUserQuestion:** текст вопроса (+ описания вариантов), кнопки `1..N`, «Другое». Несколько вопросов — по очереди (следующий после ответа на текущий). multiSelect — кнопки-переключатели ☐/☑ + «Отправить».
- «Другое» → бот просит прислать текст (force_reply); следующий текст пользователя (или reply на это сообщение) — ответ.
- **План:** заголовок + текст плана (обрезка до лимита Telegram; длинный — частями или файлом, на усмотрение строителя) + кнопки по фактическим пунктам окна + «Другое» (текст правок), если окно это поддерживает.
- **Разрешение:** инструмент + краткое описание/команда (полностью, без обрезки смысла — пользователь решает по ней), кнопки — **все пункты окна, как в терминале**, включая «Да, и больше не спрашивать» (решение пользователя).
- После ответа сообщение редактируется: кнопки убираются, дописывается «✔ выбрано: …» / «✔ отвечено в терминале» / «⌛ устарело».

### Маршрутизация входящих
1. Нажатие кнопки → диалог по callback_data (id диалога) → его сессия.
2. Reply на любое сообщение бота → сессия этого сообщения; если там открыт диалог «Другое» — это ответ, иначе — инструкция.
3. Текст без reply: если ждём «Другое» → ответ туда; иначе если одна живая сессия → в неё; иначе бот спрашивает «в какую сессию?» кнопками.
4. Инструкция = ввод текста в строку ввода сессии, пауза, Enter. Если сессия занята — Claude Code сам поставит в очередь.
   **Если в сессии открыт диалог** (вопрос/план/разрешение) — текст никогда не вводится «как есть» (цифры/буквы сработали бы по меню). Для AskUserQuestion текст = ответ «Другое» на текущий вопрос; для плана = текст правок, если окно это поддерживает; иначе бот отвечает «в сессии открыт вопрос — ответьте на него кнопками» и ничего не вводит. *(решение автора)*
4а. **AskUserQuestion с несколькими вопросами:** Telegram задаёт их по очереди, ответы копятся у демона, вводится одна последовательность на весь мастер (все вкладки + Review) после последнего ответа. «Первый побеждает» — на уровне всего диалога: если PostToolUse пришёл раньше (ответили в терминале), собранные ответы отбрасываются. Если пользователь начал отвечать в терминале частично, а затем добил в Telegram — возможен неверный ввод; его ловит сверка PostToolUse (п. 6) и сообщает ⚠. *(решение автора)*
5. Кнопка/ответ на уже закрытый диалог → «вопрос уже закрыт (ответили в терминале)», ничего не вводим.
6. После инъекции ответа на диалог демон ждёт PostToolUse ~10 с; не дождался → «⚠ не удалось подтвердить ответ, проверьте терминал».

### Команды
- `/status` — список живых сессий: проект · ветка · состояние (работает N мин / ждёт ответа / простаивает) · время последней активности.
- `/stop` — выбрать сессию (кнопками, если их > 1) → Esc в консоль. Подтверждение в ответ.
- Строитель может добавить `/help`, `/pause` `/resume` (временно не слать ничего), если дёшево.

## CLI (`cc-telegram`)
`install` (сборка, компиляция inject.exe, `.env` с плейсхолдерами + ACL, слияние хуков в settings.json с бэкапом, задача в Планировщике, старт демона), `uninstall` (обратное, хуки удаляются точечно, остальные настройки целы), `status`, `logs`, `test` (отправить тестовое сообщение), `disable`/`enable` (файл-флаг).

## Тестирование
TDD для чистой логики: маршрутизация, построение клавиатур и последовательностей клавиш (одиночный/множественный выбор, «Другое», несколько вопросов, разное N), фильтр allowlist, порог 60 с, слияние/удаление хуков в settings.json, форматирование сообщений, маскирование токена. Интеграционная проверка на живых сессиях, подтверждается реальным выводом или словами пользователя (все 6 обязательны до «готово»):
1. Уведомление о завершении пришло.
2. Тестовый AskUserQuestion: пришли кнопки, нажал «2» → сессия получила вариант 2.
3. «Другое» → текст пользователя дошёл в сессию.
4. При двух открытых проектах инструкция из бота ушла в нужную сессию.
5. Сообщение с чужого аккаунта проигнорировано.
6. После перезагрузки демон поднялся сам.
Плюс: ответ в терминале → в Telegram «✔ отвечено в терминале»; `/status`, `/stop` работают.
